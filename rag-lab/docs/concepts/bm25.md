# BM25 Keyword Search

You're building a support chatbot for a software product. A user asks: *"What does error code E4031 mean?"*

Your dense retriever embeds the query and searches for semantically similar text. The problem: `E4031` is a rare product-specific code. The embedding model has never seen it, so it produces a generic vector for "error code" — and retrieves chunks about errors in general, not the specific one.

**BM25** (Best Match 25) handles this perfectly. It doesn't use embeddings at all. It counts *exact token matches* and uses a statistical formula to rank results. `E4031` appears in exactly one chunk? BM25 finds it at rank 1, instantly.

## The formula (and why it works)

BM25 scores a document for a query using two intuitions:

1. **TF — term frequency**: if the query word appears many times in a chunk, that chunk is probably relevant.  
2. **IDF — inverse document frequency**: if a word appears in almost every chunk (like "the"), it's not discriminative. Rare words should be weighted more heavily.

BM25 combines these and adds a saturation factor so that a word appearing 100 times doesn't score 100× better than one appearing once. The full formula is:

```
score(chunk, query) = Σ  IDF(term) ×  tf × (k1 + 1)
                      terms          ─────────────────
                                     tf + k1 × (1 − b + b × len/avglen)
```

Where `k1` (default 1.5) controls term-frequency saturation and `b` (default 0.75) controls length normalisation. In practice, you never tune these — `rank-bm25` uses sensible defaults.

## Using it in RAG-Lab

```python
from rag_lab.retrieval.sparse_bm25 import BM25Retriever

retriever = BM25Retriever(index_path=".bm25_index.pkl")
results = retriever.retrieve("error code E4031", top_k=5)

for r in results:
    print(f"[{r.rank}] score={r.score:.3f}  {r.chunk.text[:80]}…")
```

The BM25 index is built by the `Indexer` (alongside the Chroma vector index) every time you run `rag-lab index`. It's a small pickle file on disk — no inference, no GPU, no network call.

## What BM25 is good at (and where it fails)

| Strength | Weakness |
|----------|----------|
| Exact token matches (IDs, codes, names) | Paraphrase / synonym queries |
| Rare, domain-specific terms | Short, vague queries |
| Fast, zero inference cost | No semantic understanding |
| Deterministic — same query always gives same result | Sensitive to stemming / tokenisation |

Dense retrieval and BM25 fail in complementary ways. A query like *"what are the side effects of ibuprofen?"* retrieves well with dense (semantic understanding) but might miss a chunk that says *"adverse reactions: nausea, dizziness…"* because it uses no query words. BM25 catches the exact-match case; dense catches the semantic case. That's why combining them with [Reciprocal Rank Fusion](fusion-rrf.md) consistently outperforms either alone.

## Tokenisation

BM25 in RAG-Lab uses whitespace tokenisation — `query.lower().split()`. This is simple and works well for English prose. For production use with medical, legal, or multilingual text, you'd want a proper tokeniser (e.g., `nltk.word_tokenize`). The `BM25Retriever` class is easy to subclass for custom tokenisation.

---

**When it matters most:** any domain with precise terminology — product codes, legal citations, medical terms, person names, version numbers. BM25 is also a great diagnostic tool: if BM25 finds a chunk easily but dense retrieval misses it, your embedding model may not have seen enough domain text during training.
